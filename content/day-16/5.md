# Rollback đúng release và giới hạn dữ liệu

## Mục tiêu

Diễn tập quay về SHA tốt đã biết, kiểm tra cả API và dữ liệu, rồi ghi rõ những gì rollback code không thể phục hồi. Không dùng “deploy lại mới nhất” làm chiến lược quay lui.

## Hiểu nhanh

Helper giữ từng release tại `releases/SHA`, chuyển symlink current và restart PM2 dưới user app. Rollback tái sử dụng cùng helper với SHA cũ đã review. Bài này không có migration schema nên code cũ vẫn dùng được bảng links hiện tại. Trong hệ thống có migration xóa cột hoặc đổi dữ liệu, đổi code không tự đưa dữ liệu quay về; cần migration tương thích, expand/contract hoặc restore theo kế hoạch riêng. Secret runtime hiện hành vẫn được lấy lại, không rollback password cũ chỉ vì code cũ.

## Thực hành

Cần hai release đã test hoặc một release hiện tại cùng artifact của SHA tốt trước đó. Trước khi thử lỗi, ghi SHA tốt, current path, vài code/URL mẫu và timestamp UTC. Không tạo lỗi bằng xóa dữ liệu. Có thể mô phỏng release lỗi ở môi trường lab riêng bằng thay đổi code đã được phép, nhưng không cần làm hệ thống đang dùng ngừng phục vụ để học quy trình.

Quản trị đọc file `shared/previous-release` mà không lộ secret, xác nhận basename đúng SHA 40 hex và archive còn trên S3. Từ phiên AWS CLI tạm của operator có quyền document/instance như role deploy:

```bash
export GOOD_SHA='THAY-SHA-TOT-DU-40-HEX'
export LAB_INSTANCE_ID='i-THAY-INSTANCE-LAB'
[[ "$GOOD_SHA" =~ ^[a-f0-9]{40}$ ]] || exit 2
ROLLBACK_COMMAND=$(aws ssm send-command \
  --document-name AwsDailyLab-Release --document-version '1' \
  --instance-ids "$LAB_INSTANCE_ID" --parameters "ReleaseSha=$GOOD_SHA" \
  --query Command.CommandId --output text)
printf 'Rollback CommandId=%s\n' "$ROLLBACK_COMMAND"
aws ssm get-command-invocation --command-id "$ROLLBACK_COMMAND" \
  --instance-id "$LAB_INSTANCE_ID" --query '{Status:Status,Code:ResponseCode}'
```

Lần query đầu có thể chưa thấy invocation; dùng vòng chờ như bài trước, không gửi command mới. Không đưa SHA vào workflow dispatch tùy ý nếu trust/provenance chưa được thiết kế: ở đây operator chọn bản phát hành đã có bằng chứng. Helper dùng lock để tránh hai thao tác cùng lúc; nếu job đầu vẫn chạy, chờ/đọc command thay vì xóa lock file.

## Kiểm tra kết quả

Trên EC2, current/RELEASE_SHA bằng GOOD_SHA, PM2 đúng user và process name, `/ready` 200. Qua tuyến public, gọi một code đã tồn tại trước deploy và kiểm Location, rồi tạo một link thử mới bằng POST `/shorten` và kiểm redirect. Count không phải bằng chứng đủ nếu URL bị đổi; so sánh vài cặp code/URL đã ghi. Nếu rollback code pass nhưng data mất, chuyển sang quy trình backup/restore ngày 14 trên DB riêng trước khi đổi endpoint; không chạy restore đè tại chỗ.

Ghi thời gian phát hiện, quyết định rollback, command accepted, app ready và public smoke pass. Đây là diễn tập có phạm vi một instance; không suy ra cả ASG đã đồng bộ. File previous-release là dấu vết gần nhất, không phải danh mục lịch sử hoàn chỉnh; giữ ledger SHA và kết quả smoke test riêng.

## Lỗi thường gặp

Release cũ yêu cầu schema đã không còn nên `/health` có thể sống nhưng `/ready` hoặc request DB lỗi. Artifact đã bị lifecycle xóa thì không thể dựng lại máy mới chỉ bằng symlink cũ. Đổi database password cùng lúc release lỗi làm khó phân loại; giữ quy trình rotation có kiểm tra độc lập. Không bỏ TLS verification để “cứu” rollback.

## Dọn dẹp

Sau khi đã xác nhận bản tốt, liệt kê release directories và object keys, giữ current cùng ít nhất một bản rollback đã biết. Xóa từng SHA không dùng bằng hành động chủ động sau review; không có script xóa broad trong giáo trình. Nếu kết thúc lab, dừng app, teardown EC2/RDS/ALB và các phụ thuộc theo tuyến chính, xóa đúng artifacts/parameters/document/roles riêng của ngày 16. Kiểm tra manual snapshots, NAT, interface endpoints, EBS và logs còn lại vì rollback không dọn hạ tầng và không chặn chi phí.
