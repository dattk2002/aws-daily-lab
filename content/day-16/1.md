# OIDC với repo, branch và audience chính xác

## Mục tiêu

Thiết kế danh tính deploy tạm thời của GitHub Actions, giới hạn đúng repository và branch `main`. Bài không tạo AWS access key và không cấp cho CI pull request quyền deploy. Năm bài ngày này là một lab liên hoàn; chỉ chạy workflow sau khi mọi bước chuẩn bị đã hoàn thành.

## Hiểu nhanh

OIDC cho AWS xác minh token do GitHub phát hành rồi cấp phiên STS ngắn hạn. Trust policy trả lời ai được assume role; permission policy trả lời phiên role được gọi API nào. Trong lab có ba danh tính: người quản trị tạo hạ tầng; role GitHub upload artifact/gửi command; instance role tải artifact/đọc secret. Role GitHub không đọc mật khẩu RDS. Quyền chạy một SSM document vẫn là quyền mạnh, vì document cuối cùng điều khiển code chạy trên máy.

## Thực hành

Quản trị viên thêm IAM OIDC provider `https://token.actions.githubusercontent.com` với audience `sts.amazonaws.com` nếu account chưa có; tái sử dụng provider đúng thay vì tạo bản trùng. Tạo role ví dụ `aws-daily-lab-github-deploy`. Thay account ID và subject trong trust policy này:

```json
{
  "Version":"2012-10-17",
  "Statement":[{
    "Effect":"Allow",
    "Principal":{"Federated":"arn:aws:iam::ACCOUNT_ID:oidc-provider/token.actions.githubusercontent.com"},
    "Action":"sts:AssumeRoleWithWebIdentity",
    "Condition":{"StringEquals":{
      "token.actions.githubusercontent.com:aud":"sts.amazonaws.com",
      "token.actions.githubusercontent.com:sub":"repo:OWNER/REPO:ref:refs/heads/main"
    }}
  }]
}
```

Không mặc định subject định dạng cũ. Tài liệu GitHub hiện nêu repo tạo sau 15/07/2026 hoặc đã opt-in immutable subject có dạng `repo:OWNER@OWNER_ID/REPO@REPO_ID:ref:refs/heads/main`. Xem cấu hình OIDC và định dạng subject áp dụng cho chính repo, thay chính xác cả IDs nếu cần. Không sửa thành wildcard để tránh tìm nguyên nhân. Job lab không khai báo `environment:` vì nó đổi dạng subject; nếu thêm environment, phải thiết kế lại trust cùng branch protections theo tài liệu, không dùng nguyên policy trên.

Permission policy của role deploy dùng đúng Region/account/bucket/instance/document đã ghi:

```json
{
  "Version":"2012-10-17",
  "Statement":[
    {"Effect":"Allow","Action":"s3:PutObject",
     "Resource":"arn:aws:s3:::BUCKET_LAB/releases/*"},
    {"Effect":"Allow","Action":"ssm:SendCommand","Resource":[
      "arn:aws:ssm:REGION:ACCOUNT_ID:document/AwsDailyLab-Release",
      "arn:aws:ec2:REGION:ACCOUNT_ID:instance/INSTANCE_ID"]},
    {"Effect":"Allow","Action":"ssm:GetCommandInvocation","Resource":"*"}
  ]
}
```

`GetCommandInvocation` cần `Resource: *` theo phạm vi API; không biến các action khác thành wildcard. Không cấp `iam:PassRole`, EC2 terminate hoặc RDS modify cho workflow này. Branch main phải được bảo vệ/review vì source workflow trên branch có thể sử dụng role.

## Kiểm tra kết quả

Ghi bảng phân quyền: GitHub PutObject releases + gửi đúng document; EC2 GetObject releases + GetParameter runtime; quản trị tạo role/document. Ở bài 4, `sts get-caller-identity` phải là assumed role đúng account. Nhánh khác không được assume. Không in JWT hoặc access keys để debug, chỉ kiểm tra subject format bằng phương thức không tiết lộ token.

## Lỗi thường gặp

Sai account trong provider ARN làm STS từ chối. `id-token: write` của workflow cho phép yêu cầu token, không tự cấp S3. Thêm environment đổi sub nên policy branch cũ không match. Dùng repository rename với immutable IDs cần đọc chính xác claim thay vì đoán.

## Dọn dẹp

Bài thiết kế không tạo compute; IAM/OIDC không có phí compute riêng, còn S3/EC2/endpoint sẽ có phí khi dùng. Giữ role cho lab, rồi tháo policy/role riêng khi kết thúc. Không xóa OIDC provider dùng chung bởi workflow khác. Không gắn role deploy vào root website Pages workflow: deploy ứng dụng và publish website là hai việc riêng.
