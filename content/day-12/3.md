# Reboot và dữ liệu tồn tại

## Mục tiêu
Chứng minh app và Nginx tự trở lại sau EC2 reboot, link đã lưu trong RDS vẫn redirect đúng. Bài gây gián đoạn tạm thời trên EC2 lab duy nhất; không thực hiện khi máy đang phục vụ người khác hoặc đang cài update chưa hoàn thành.
## Hiểu nhanh
`pm2 start` chỉ chạy process hiện tại; tự khởi động lại sau reboot cần PM2 startup service và process list đã `pm2 save` bằng đúng user. Nginx cũng cần systemd enabled. RDS tách khỏi EC2 nên reboot EC2 không nên làm mất hàng trong bảng links; song app phải còn đọc được file runtime và CA bundle TLS sau boot.
Reboot khác stop/start và khác terminate. Không dùng terminate để thử khả năng reboot. ALB có thể báo target unhealthy trong thời gian máy khởi động; một target không bảo đảm không gián đoạn. “Không lỗi trong lần thử này” không chứng minh zero downtime. Dùng code có thật từ 12-1 để kiểm tra persistence, không tự tạo code mới rồi gọi đó là dữ liệu cũ.
## Thực hành
Các lệnh AWS CLI dưới đây chạy trong shell máy cá nhân với profile `lab` đã cấu hình ở 02-5. Mỗi khi mở shell mới, đặt lại `export AWS_PROFILE=lab`, khôi phục các biến ID/Region từ sổ lab và kiểm tra identity trước mutation. Không đặt profile cá nhân này trên EC2 hoặc trong cấu hình CloudWatch agent; các tiến trình đó dùng instance role.

Trước reboot, trong shell non-root app user kiểm tra process rồi lưu danh sách. File PM2 dump có thể chứa biến môi trường nên giữ riêng trong home user, không upload hoặc commit:
```bash
pm2 status
pm2 save
```
Trong phiên quản trị EC2, điền username thực đã dùng ngày 7, không tạo user mới chỉ để khớp ví dụ:
```bash
export LAB_APP_USER=TEN_USER_APP_THAT
sudo systemctl is-enabled nginx
sudo systemctl is-enabled "pm2-$LAB_APP_USER"
sudo systemctl status "pm2-$LAB_APP_USER" --no-pager
```
Nếu PM2 service chưa tồn tại/enabled, quay lại bước `pm2 startup` ngày 7 và thực hiện đúng lệnh systemd PM2 tạo cho user/home thực, rồi `pm2 save`; không chạy tất cả app dưới root. Kiểm tra file runtime/CA còn đúng quyền và path, không in nội dung secret. Từ laptop ghi link cũ và timestamp; xác minh redirect trước reboot.
Sau khi đã sẵn sàng, dùng CLI quyền người triển khai, đúng instance ID:
```bash
export AWS_PROFILE=lab
aws ec2 describe-instances --instance-ids "$LAB_INSTANCE_ID" \
  --query 'Reservations[].Instances[].{Id:InstanceId,Name:Tags,State:State.Name}'
aws ec2 reboot-instances --instance-ids "$LAB_INSTANCE_ID"
```
Theo dõi Instance console/system log hoặc SSM reconnect. `instance-status-ok` có thể trả ngay khi checks chưa phản ánh reboot, nên waiter không phải chứng cứ duy nhất. Sau khi kết nối lại, chạy `uptime -s` để xác minh boot mới; kiểm tra:
```bash
sudo systemctl is-active nginx
# Trong shell đúng app user:
pm2 status
curl -i --max-time 10 http://127.0.0.1/ready
```
Từ laptop kiểm tra `/ready` qua `$LAB_BASE_URL`, sau đó `GET /r/$LAB_CODE` cũ với curl không follow và tạo thêm một link mới. Theo dõi target group trở lại healthy.
## Kiểm tra kết quả
Có giờ boot mới, Nginx active, PM2 app online đúng user, local/external readiness 200, target healthy và link trước reboot vẫn 302 đúng Location. Ghi downtime quan sát được giữa request cuối tốt và request tốt trở lại, nhưng nêu tần suất lấy mẫu nên đây không phải phép đo tuyệt đối. Không gọi “đã chịu lỗi AZ” sau một lần reboot một instance.
## Lỗi thường gặp
PM2 daemon root có app online nhưng daemon user app trống là dấu hiệu chạy nhầm user. `pm2 save` trước khi app đúng cấu hình có thể lưu process list sai. File `.env` hoặc PGSSLROOTCERT đặt ở `/tmp` có thể không bền vững; chuyển theo quy trình runtime bảo vệ ngày 7. Nginx active mà Node chưa lên có thể trả 502, dùng error log và `journalctl -u pm2-USER` để xác minh.
## Dọn dẹp
Giữ app online, target healthy và link cũ cho bằng chứng. Nếu startup thất bại, khôi phục dịch vụ trước khi rời bài, hoặc thực hiện teardown có kiểm soát ở 12-5. Reboot không dừng phí EC2, EBS, RDS hoặc ALB. Không tạo snapshot/AMI tự động vì các tài nguyên đó có vòng đời và phí riêng.
