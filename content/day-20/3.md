# Capstone: đo, gây lỗi local và giải thích

## Mục tiêu

Chạy test đúng hợp đồng API, đo mẫu nhỏ có giới hạn rồi gây lỗi DB local và khôi phục. Không dừng RDS thật chỉ để hoàn thành challenge; lỗi local đủ chứng minh cách phân biệt liveness/readiness, còn lỗi cloud phải có kế hoạch riêng.

## Hiểu nhanh

Một lần trả200 không chứng minh hệ thống đáng tin. Cần kiểm tra tạo dữ liệu, đọc lại, redirect và phản ứng khi phụ thuộc mất. Mẫu30 request tuần tự chỉ mô tả cửa sổ đo đó, không phải benchmark khả năng tối đa hoặc SLA. Khi DB mất, `/health` còn200 là dự kiến nếu Node vẫn sống; `/ready`503 cho biết chưa phục vụ được công việc cần DB.

## Thực hành

1. Cần app local đang chạy, container PostgreSQL đã ready và schema đã init từ20-2. Terminal thứ hai đặt BASE local; khi chỉ chạy smoke cloud có thể thay hostname/domain thật, nhưng các bước gây lỗi4–5 luôn dành cho Compose local:

```bash
BASE='http://127.0.0.1:3000'
curl -sS -i --max-time 5 "$BASE/health"
curl -sS -i --max-time 5 "$BASE/ready"
curl -sS -i --max-time 5 "$BASE/shorten" \
  -H 'Content-Type: application/json' \
  --data '{"url":"https://example.com"}'
CODE='MA_THUC_NHAN_TU_RESPONSE'
curl -sS -D - -o /dev/null --max-time 5 "$BASE/r/$CODE"
curl -sS -i --max-time 5 "$BASE/r/unknown-capstone-code"
```

Mong đợi lần lượt200,200,201,302 với Location gốc,404. Không dùng `-L` cho phép thử302. Xác minh mã unknown thực sự chưa tồn tại; nếu đã dùng trong dữ liệu trước, chọn mã khác.
2. Đo30 request có giới hạn, không chạy background hoặc tự tăng concurrency:

```bash
for i in {1..30}; do
  curl -sS -o /dev/null --max-time 3 \
    -w '%{http_code},%{time_total}\n' "$BASE/ready"
  sleep 0.2
done
```

Ghi số2xx/5xx/timeouts và khoảng thời gian, không điền sẵn số đẹp. `curl` timeout có thể báo status000, không phải mã HTTP server trả. Nếu muốn p95, sắp xếp các duration thành công và nói rõ cách tính/sample size; không trộn timeout3 giây vào0.
3. Giữ `code` đã tạo và response trước lỗi. Kiểm tra BASE vẫn là localhost; tuyệt đối không suy rộng lệnh stop sang cloud.
4. Tại `labs/url-shortener`, `docker compose -f compose.yaml stop` chỉ dừng stack DB local của demo, không xóa volume. Node chạy terminal khác vẫn sống. Gọi lại `/health`, `/ready` và `POST /shorten` trong timeout5 giây. Ghi status thực tế và log đã che cấu hình; mong đợi health200, ready503, request phụ thuộc DB không thành công. Nếu khác, giải thích bằng code/log, không chỉnh chứng cứ.
5. Chạy `docker compose -f compose.yaml up -d --wait`, chờ PostgreSQL ready rồi gọi `/ready`. Kiểm tra redirect với code cũ, mong đợi302 sau phục hồi vì volume còn dữ liệu. Nếu pool/app chưa phục hồi, thu log rồi restart local app bằng Ctrl+C và `npm start`; ghi rõ cần restart, không gọi đó là tự hồi phục.

## Kiểm tra kết quả

Hồ sơ cần ba pha trước lỗi/trong lỗi/sau phục hồi, có code link cũ và mốc thời gian. Giải thích được vì sao `links` không mất khi stop/start container nhưng có thể mất nếu xóa volume. Với cloud smoke, ghi rõ tuyến request thực đi qua ALB; lỗi local không chứng minh ASG/RDS failover thực đã test.

## Lỗi thường gặp

Đổi BASE sang ALB rồi quên quay về local khi ghi fault result làm hai phép đo không so sánh được. Coi30 request tuần tự là bài load test production không có căn cứ. Dùng `docker compose down -v` phá dữ liệu làm bài “khôi phục” không còn cùng điều kiện. Chỉ nhìn log không ghép request ID/thời điểm dễ nhầm lỗi từ lần chạy trước.

## Dọn dẹp

Kết thúc fault test phải đưa DB local về trạng thái tốt hoặc ghi rõ đã dừng. Ctrl+C dừng Node và `docker compose -f compose.yaml down` dừng container khi không cần; giữ volume tới quyết định xóa dữ liệu ở20-5. Không có tài nguyên AWS mới do fault local. Nếu đang giữ cloud để smoke, thu bằng chứng xong tiến hành teardown, không bật tải qua đêm.
