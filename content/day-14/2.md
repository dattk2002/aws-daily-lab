# Snapshot và PITR tạo DB mới

## Mục tiêu

Tạo một manual snapshot và lập lệnh phục hồi vào một DB private mới có tên riêng. Chỉ chọn chạy một nhánh restore sau khi xem chi phí; không cần tạo cả snapshot restore lẫn PITR cùng lúc.

## Hiểu nhanh

Snapshot là điểm chụp cấp instance; PITR chọn thời điểm trong khoảng RDS cho phép. Cả hai tạo instance mới với endpoint mới. Ứng dụng không tự chuyển sang endpoint đó. Restore cũng cần xem lại subnet group, Security Group, instance class, parameter group và encryption/KMS; không dựa vào default VPC. Trong bài, DB mới chỉ cho EC2 lab kết nối TLS và không public.

## Thực hành

Cần DB nguồn từ tuyến chính, subnet group private hai AZ và SG đã cho phép nguồn EC2. Điền ID thật, kiểm tra tài nguyên trong Region đang chọn. Snapshot và instance mới đều có thể tính phí:

```bash
export LAB_SNAPSHOT='aws-daily-lab-day14-manual'
export RESTORE_DB_ID='aws-daily-lab-day14-restore'
aws rds create-db-snapshot --db-instance-identifier "$LAB_DB_ID" \
  --db-snapshot-identifier "$LAB_SNAPSHOT"
aws rds wait db-snapshot-available --db-snapshot-identifier "$LAB_SNAPSHOT"
```

Giả sử dùng class tương thích nguồn và đã thay mọi placeholder, nhánh snapshot restore:

```bash
aws rds restore-db-instance-from-db-snapshot \
  --db-instance-identifier "$RESTORE_DB_ID" \
  --db-snapshot-identifier "$LAB_SNAPSHOT" \
  --db-instance-class 'THAY-CLASS-TUONG-THICH' \
  --db-subnet-group-name 'THAY-SUBNET-GROUP-PRIVATE' \
  --vpc-security-group-ids 'sg-THAY-SG-RDS-LAB' \
  --no-publicly-accessible
```

Nếu chọn PITR, thay lệnh restore trên bằng lệnh dưới và lấy thời điểm UTC nằm trong earliest/latest của bài trước:

```bash
aws rds restore-db-instance-to-point-in-time \
  --source-db-instance-identifier "$LAB_DB_ID" \
  --target-db-instance-identifier "$RESTORE_DB_ID" \
  --restore-time 'THAY-THOI-DIEM-UTC-ISO8601' \
  --db-instance-class 'THAY-CLASS-TUONG-THICH' \
  --db-subnet-group-name 'THAY-SUBNET-GROUP-PRIVATE' \
  --vpc-security-group-ids 'sg-THAY-SG-RDS-LAB' \
  --no-publicly-accessible
```

Không chạy cả hai với cùng target name. Nếu nguồn có custom parameter group, KMS hoặc cấu hình đặc biệt, rà tài liệu và thêm tham số tương ứng trước khi chạy.

## Kiểm tra kết quả

Đợi `db-instance-available`, đọc endpoint và `PubliclyAccessible=false`. Từ EC2 đã được phép kết nối, dùng `psql` TLS `verify-full` với CA RDS đã chuẩn bị để chạy `SELECT count(*) FROM links;`. So sánh một code/URL mẫu trước snapshot hoặc mốc PITR. Một status Available không chứng minh schema và dữ liệu đúng.

## Lỗi thường gặp

Chọn thời điểm sau LatestRestorableTime gây lỗi; đừng đổi timezone bằng cách bỏ hậu tố UTC. Restore sang default SG làm ứng dụng timeout dù DB khỏe. Endpoint khác nhưng password/role có thể như tại mốc backup, cần kiểm tra theo quy trình secrets thay vì in mật khẩu. Không nhầm S3 snapshot export với tài nguyên snapshot RDS có thể restore.

## Dọn dẹp

Sau khi đã thu bằng chứng và không còn dùng DB restore, xác nhận đúng tên `aws-daily-lab-day14-restore`, rồi xóa trong console với lựa chọn backup phù hợp. Nếu chủ động bỏ dữ liệu thử: `aws rds delete-db-instance --db-instance-identifier "$RESTORE_DB_ID" --skip-final-snapshot --delete-automated-backups`. Lệnh có chủ ý mất dữ liệu target, không được dùng cho DB nguồn. Xóa snapshot lab đúng tên bằng `delete-db-snapshot` khi hết cần; storage snapshot còn lại có thể tiếp tục tính phí.
