# Vào máy bằng SSH hoặc Session Manager

## Mục tiêu

Mở được phiên quản trị tới đúng máy lab, xác minh danh tính hệ điều hành và phân biệt được đường SSH với Session Manager. Không đưa private key lên EC2 và không dùng root làm tài khoản làm việc hằng ngày.

## Hiểu nhanh

SSH xác thực bằng key pair và cần đường TCP 22 tới máy. Session Manager mở phiên qua SSM Agent, IAM và HTTPS outbound; nó không tự hoạt động chỉ vì máy mang nhãn EC2. Cả hai là quyền quản trị mạnh, khác quyền mà process ứng dụng cần. App ở ngày 07 sẽ chạy bằng user riêng, không mang quyền sudo của phiên quản trị.

Nhánh SSH dưới đây cần key pair đã chọn khi launch, client OpenSSH trên máy cá nhân, public IP hiện tại của EC2 và rule 22 từ IP của bạn. Nhánh SSM cần SSM Agent hoạt động, instance profile có quyền managed-instance phù hợp, người mở phiên có quyền Session Manager, và mạng outbound HTTPS tới các endpoint SSM cần thiết. Dùng Internet/NAT hoặc VPC endpoints có chủ đích; endpoints/NAT có thể phát sinh phí riêng. Không bật thêm cả hai nhánh chỉ để thử may rủi.

## Thực hành

Với SSH, giữ private key trên máy cá nhân, hạn chế quyền file rồi kết nối:

```bash
chmod 400 ~/.ssh/aws-daily-lab.pem
ssh -i ~/.ssh/aws-daily-lab.pem ec2-user@<EC2_PUBLIC_IP>
```

Thay placeholder; không chạy lệnh trên EC2. Lần đầu, đối chiếu fingerprint host key bằng kênh AWS đáng tin cậy trước khi chấp nhận, không vô hiệu hóa StrictHostKeyChecking. Nếu IP nhà đổi, sửa rule `/32` tới đúng IP mới trước khi thử lại.

Với SSM, mở Systems Manager → Session Manager, chọn đúng instance ID và Start session. Nếu không thấy target, kiểm tra Managed nodes, IAM profile, trạng thái agent và outbound trước. Khi có shell, chạy:

```bash
whoami
hostname
cat /etc/os-release
uname -m
```

Đối chiếu AL2023 và kiến trúc với phiếu ngày 05-1. Với SSM, user có thể là `ssm-user`; dùng `sudo -iu ec2-user` để các bước quản trị sau nhất quán. Ghi phương thức đăng nhập vào runbook, tuyệt đối không ghi nội dung private key.

## Kiểm tra kết quả

Một phiên hợp lệ phải khớp instance ID bạn chọn, AL2023 và kiến trúc dự kiến. Thoát bằng `exit`, mở phiên thứ hai để chứng minh cách vào máy có thể lặp lại. Không sửa SG của phiên đang dùng trước khi biết đường kết nối thay thế hoạt động.

## Lỗi thường gặp

`Permission denied (publickey)` thường liên quan key hoặc user; AL2023 dùng `ec2-user`, không dùng `ubuntu`. Timeout thường ở IP/route/SG hơn là key. SSM target offline không được sửa bằng cách mở 22 toàn Internet; quyền IAM, agent và kết nối HTTPS là chuỗi khác cần kiểm tra.

## Dọn dẹp

Đóng phiên sau khi làm việc. Giữ key an toàn và chỉ giữ rule SSH khi còn cần; với SSM đã xác minh có thể xóa rule 22 của riêng lab. Không xóa file key duy nhất trước khi biết phương án khôi phục. Giữ EC2 cho bài tiếp theo, hoặc terminate và kiểm tra EBS nếu kết thúc lab.
