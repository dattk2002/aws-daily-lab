# Đọc access log và error log theo một request

## Mục tiêu

Tìm một request thử trong log Nginx, phân biệt status do upstream trả với lỗi kết nối upstream và liên hệ thời điểm với log PM2. Không đưa secrets hoặc URL cá nhân vào bằng chứng chia sẻ.

## Hiểu nhanh

Access log trả lời request nào được xử lý và status ra sao; error log giải thích sự cố như không kết nối được upstream. App log có góc nhìn khác, ví dụ lỗi truy vấn database. Không có access line có thể nghĩa request chưa tới Nginx, nhưng cũng có thể do bạn đọc sai file hoặc log bị buffer; phải kiểm tra cấu hình đang áp dụng.

Mẫu repository dùng log riêng cho lab. Xác nhận đường dẫn qua `sudo nginx -T` trước khi đọc; không giả định mọi bản cài ghi cùng chỗ. URL và query string có thể chứa dữ liệu nhạy cảm ngay cả khi request body không được ghi. Chỉ test với `example.com`, không gửi credentials trong URL và không tải log thô lên issue public.

## Thực hành

1. Tìm các dòng `access_log` và `error_log` của server demo trong cấu hình đang chạy. Nếu theo mẫu mặc định của lab, đọc hai file dưới đây; nếu đã thay đường dẫn hãy dùng đúng đường thực tế:

```bash
sudo tail -n 20 /var/log/nginx/aws-daily-lab.access.log
sudo tail -n 20 /var/log/nginx/aws-daily-lab.error.log
date -u
curl -i 'http://127.0.0.1/health?trace=day08-check'
```

2. Đọc lại access log và tìm URI có `trace=day08-check`. Ghi UTC time, method, path, status và số byte; không cần IP người dùng thật. Query vô hại này giúp phân biệt request vừa gửi với traffic khác.
3. Nếu muốn đo upstream, thêm một `log_format` riêng trong ngữ cảnh `http` được include, không nhét vào `location`:

```nginx
log_format lab_timing '$time_iso8601 $request_method $uri $status '
                      'upstream=$upstream_status total=$request_time '
                      'upstream_time=$upstream_response_time';
```

Tham chiếu `lab_timing` trong directive access_log của server lab, rồi test syntax/reload. Format này dùng `$uri` để không ghi query string; không ghi body, cookie hay Authorization. Chạy thêm health và một `/r/<MA_KHONG_TON_TAI>` để so sánh 200/404. Trong shell app user, xem `/home/labapp/.local/bin/pm2 logs aws-daily-lab --lines 20 --nostream` khi cần đối chiếu.

## Kiểm tra kết quả

Health có access line status 200; route mã thiếu có 404 và upstream status tương ứng khi format timing đã bật. Một request 404 bình thường không bắt buộc có error line. Chênh lệch total và upstream time là tín hiệu để điều tra, không tự kết luận mạng chậm. Lưu trích đoạn nhỏ đã che IP/host riêng tư, đồng bộ múi giờ trước khi ghép PM2 và Nginx logs.

## Lỗi thường gặp

`unknown log format` xuất hiện khi format chưa được định nghĩa trước nơi dùng hoặc sai context. Error log trống không chứng minh DB tốt; app có thể xử lý lỗi và trả 503 hợp lệ. Quyền đọc log của admin không có nghĩa cần chmod 777 hoặc cấp app user quyền sửa log hệ thống.

## Dọn dẹp

Không truncate log khi đang điều tra. Kiểm tra rotation package bằng `sudo logrotate -d /etc/logrotate.d/nginx` nếu file này tồn tại; đây là chế độ debug, không ép rotate. Với tên log riêng, kiểm tra pattern rotation bao phủ chúng để đĩa không tăng vô hạn. Giữ log cần thiết trong thời gian hợp lý, gỡ thông tin nhạy cảm khỏi tài liệu chia sẻ và dọn cloud khi kết thúc lab.
